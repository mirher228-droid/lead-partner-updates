# Аудит надёжности общей панели Авито

Это аудит первого этапа. Описанный ниже следующий этап ограничения кэшей выполнен;
расширенные исправления и пятичасовой прогон описаны в `reliability-extended.md`
и `reliability-extended-validation.md`. Исходные выводы сохранены для прослеживаемости.

Проверяемая исходная копия: Common **1.2.50**, коммит
`0cdd091e417268cfe1bd5df7a00ab71d9e23ad93`.
Это анализ исходников и автономные проверки. Версии расширения на компьютерах
сотрудников, реальные сеансы CRM и фактическая установка обновлений не проверялись.
Публикация выпуска, изменение номера версии и ключа расширения не выполнялись.

## Как устроена действующая цепочка

В исходной поставке 92 файла, из них 64 JavaScript. Статический граф подключений
из manifest, HTML и importScripts приводит к 33 JS-файлам; 31 старый вспомогательный
JS-файл не имеет действующей точки подключения в этой копии. Наличие таймера
в таком старом файле само по себе не означает нагрузку в панели.

разбора совместимости установщика и старых пакетов не даёт доказанного ускорения.

## Подтверждённые проблемы и исправления

### 1. Разные операции создания обходили общую блокировку

Обычный путь create/update записывал результат в background после ответа сервера,
но не вызывал begin/dispatch перед записью. Локальная защита CRM-сервиса различала
операции по UUID: две вкладки одного контекста могли войти в работу параллельно.

Подключён существующий долговременный gate: begin, подтверждение dispatch перед
первой записью и ожидание finish. При неизвестном исходе другая операция не получает
разрешение на отправку. Результат старой операции не может затереть новый цикл.
Отдельно проверяется намеренное создание повторной заявки после завершённой.
Это защита в пределах общего хранилища данного расширения/контекста, а не серверная
гарантия отсутствия дублей между разными компьютерами и сотрудниками.

Проверки: `tests/controller-write.test.cjs`, `tests/request-gate.test.cjs`.

### 2. Неопределённое сохранение исчезало из состояния панели

Панель сбрасывала operation при uncertain, исключении транспорта и повторном
открытии. Элементы проверки результата также были скрыты. В итоге прежний UUID
терялся для UI, хотя сервер мог принять запись.

Незавершённая операция и отправленные данные теперь сохраняются для проверки
результата. Восстановление проверяет долговременный статус и принадлежность клиенту.
Подтверждённый результат обязан соответствовать нужной базе и точному номеру.
Безопасный отказ до записи позволяет исправить форму; неопределённость продолжает
блокировать новую отправку. Поздний ответ относится к исходному диалогу.

Проверки настоящего DOM в Chromium: `tests/panel-recovery.test.cjs`.
Сеть, controller и хранилище заменены искусственными границами: это проверка панели,
а не подтверждение совместимости с живой CRM.

### 3. «Проверить результат» могло выполнять дополнительные изменения

В старом reconcile имелись продолжения сохранения комментариев, источника и
нативной отмены; одно нативное действие использует GET, который тоже меняет статус.
Поэтому одного запрета POST недостаточно.

Controller запускает reconcile с readOnly по умолчанию. Сервис читает доказательства,
но не отправляет незавершённые изменяющие действия автоматически. Если они необходимы,
результат остаётся uncertain с объяснением и блокировкой. Уже сохранённые поля можно
подтвердить чтением. Обычный намеренный save и прежний прямой API сервиса без readOnly
сохраняют совместимость; явный выпуск после этой работы требует проверки сценариев ниже.

Прежнее намеренное действие отмены с автоматически выбранной бизнес-правилами
причиной остаётся отдельным сценарием. Его сохранённый этап awaiting_reason может
продолжаться после перезагрузки, как раньше; это не режим reconcile и не разрешение
повторять запись с неизвестным результатом.

Проверки: `tests/crm-reconcile.test.cjs`, включая нативный изменяющий GET.

### 4. Расписание использовало ответ от другого времени

Запрос timetable зависел от базы, города, даты **и времени**, а ключ кэша — только
от первых трёх значений. Воспроизведение: 10:00 → 15:00 в течение TTL возвращало
ответ для 10:00. Время добавлено в ключ; одинаковые параллельные чтения по-прежнему
объединяются. Проверки: `tests/crm-timetable.test.cjs`.

### 5. Медленное чтение могло откатить каталог

После запуска initial storage.get мог завершиться позже новой onChanged и
заменить свежий каталог старым. Счётчик принятых обновлений предотвращает такое
затирание, в том числе когда содержимое одинаковое, но revision новее.
Непроверенные записи по-прежнему отвергаются.
Проверки: `tests/source-catalog.test.cjs`.

### 6. Невидимая вкладка продолжала обходить страницу

Страховочный интервал выполнял ensureButton каждые 3,5 секунды даже при hidden.
В контролируемом DOM 50 срабатываний приводили к 200 лишним обращениям к селекторам.
Теперь hidden пропускает таймер и планирование observer, уже поставленный rAF также
перепроверяет видимость; при возврате выполняется синхронизация.

Убран второй запрос контекста при первом создании панели таймером/observer;
подписка использует уже подтверждённый контекст. Сохранение iframe при замене
SPA-разметки и возвращении в диалог проверяется отдельно.
Это измерение количества вызовов в тесте, не процент ускорения рабочего ПК.
Проверки: `tests/request-host.test.cjs`.

### 7. ZIP мог собраться без необходимых модулей панели

Раньше сборка проверяла ресурсы manifest, но пропускала зависимости HTML и
literal importScripts service worker. Удаление panel.js, panel.css или импортируемого
worker-модуля не мешало получить ZIP. Добавлена проверка этих ссылок и
web_accessible_resources. Неполный пакет не доходит до создания архива.
Проверка importScripts намеренно ограничена используемой в проекте формой
literal top-level calls и не выдаётся за полный анализатор JavaScript.

Проверки: `tests/test_cloud_build.py`. Новые Node/Chromium-проверки включены
в cloud workflow; это изменение конфигурации CI, не утверждение о запуске GitHub Actions.

## Что уже работало и сохранено

- Проверки отправителя, origin, канала iframe и допустимых CRM-адресов.
- Проверка CSRF, ожидаемой ревизии, точного номера и полей ответа.
- Объединение одинаковых чтений и короткий TTL нативных форм.
- Отмена общих запросов карт с учётом оставшихся подписчиков; ограниченные кэши карт.
- Защита справочника от повреждённых записей, устаревших ответов сервиса и резкого обнуления.
- Номер версии, manifest key, permissions, внешний вид и старый канал обновления.

## Оставшиеся ограничения и следующий этап

1. **Память при очень долгой работе.** В автономном прогоне 1000 диалогов сохранили
   1000 сервисов и записи нескольких контекстных Map. Это подтверждает отсутствие
   ограничения количества контекстов, но не измеряет байты в рабочем браузере.
   Следующий отдельный шаг — жизненный цикл/LRU только для временных чтений с
   закреплением активных операций. Долговременные журналы нельзя очищать вместе
   с кэшем: от них зависит предотвращение повторной записи.
   Подписка адаптера контекста также может вызывать DOM-работу в скрытой вкладке;
   в этом изменении убраны регулярный таймер и observer, а не все возможные события.
2. **Неопределённая частичная запись.** Без серверного idempotency key нельзя
   гарантировать исход потерянного ответа. Теперь приоритет — не повторять
   изменение вслепую. Иногда потребуется ручная проверка карточки в CRM.
3. **Живые формы и внешние сервисы.** Изменение HTML CRM, авторизации, session policy
   или формата страниц Яндекса может требовать адаптации. Автономные фикстуры этого
   не доказывают; реальные CRM-запросы и Telegram не выполнялись.
4. **Windows и выпуск.** Существующие Windows-проверки остаются в GitHub Actions.
   Перед отдельной командой на выпуск нужно проверить точный ZIP Windows-валидатором
   и пройти ручные сценарии; затем выпустить новую версию по существующим правилам.

## Ручная приёмка перед разрешением выпуска

На тестовой CRM/разрешённом стенде, без заявок реальных сотрудников:

- Открыть/переключить диалог, сменить базу, набрать черновик, скрыть/вернуть вкладку.
- Создать заявку, открыть тот же диалог во второй вкладке; убедиться, что повторный
  клик не запускает вторую запись. Искусственно задержать ответ и перезагрузить панель.
- Проверить восстановление точного номера, отказ в принятии чужой карточки и
  сохранение введённых правок после неопределённого исхода.
- Из сохранённой и найденной карточки отдельно открыть повтор/гарантию.
- Проверить обычное редактирование, перенос, отмену с причиной и претензию для
  разрешённых баз. Убедиться, что фоновая проверка результата не меняет поля.
- Для источника, расписания и адреса проверить смену значения во время медленного
  ответа: прежний ответ не должен заменять текущий выбор.

Команды автономной проверки и их окончательные результаты приведены в
`reliability-validation.md` после завершения независимого ревью.
