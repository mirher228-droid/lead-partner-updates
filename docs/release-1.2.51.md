# Общая версия 1.2.51

Сохранены привычный интерфейс, настройки и идентификатор общей панели Авито.

- Исправлено определение КП/МНЧ/БТ по меткам профиля и услугам, включая
  смешанные русские и латинские буквы. При сравнении учитывается каталог
  нужного партнёра; ошибка CRM не выдаётся за пустой список другой базы.
- Убраны повторные чтения при открытии карточки и лишняя загрузка форм
  и расписания во время сравнения баз. Одинаковые проверки объединяются.
- Черновики и ручной выбор защищены при смене диалога, загрузке новых данных
  и поздних ответах. Черновик одного клиента не переносится другому.
- Усилено восстановление после неопределённого результата сохранения,
  чтобы не отправлять ту же заявку повторно. Недействительный контекст
  блокирует действия; после восстановления панель продолжает работу.
- Ограничен рост временных кэшей и уменьшена фоновая нагрузка скрытой вкладки.
  Исправлены гонки каталога источников и проверка повреждённых границ карты.

Изменения проверены на искусственных данных с настоящим Chromium. Живые
заявки в CRM при проверках не создавались; это не заявление о проверке
каждого рабочего компьютера.

Если автообновлятор уже установлен, пакет загрузится при очередной проверке
и применится после полного закрытия браузера. Переустановка расширения
и новые разрешения не требуются.

## Подготовка и порядок публикации

Этот документ подготовлен до выпуска. Факт публикации подтверждают успешные
Actions и итоговая проверка общедоступного канала, а не наличие этого файла.

1. Обновить только номер версии manifest до 1.2.51. Ключ и разрешения должны
   совпадать с неизменяемым архивом Common 1.2.50.
2. Сохранить чужие изменения, получить актуальный main и отправить release
   commit с исходниками, тестами и workflow `publish-common-1.2.51.yml`.
3. Публикующий workflow вызывает `cloud-common.yml` как обязательный build job
   через `workflow_call` на том же SHA. Windows выполняет Node/Chromium и
   Python-проверки, собирает ZIP и проверяет его через `Test-CommonArchive`.
   Используется единственный ZIP артефакта `common-test-build` текущего run,
   без повторной сборки на публикующем шаге.
4. Выполнить семь существующих Windows PowerShell 5.1 suites. Сверить inventory
   ZIP с checkout, версию, ключ и разрешения. Построить setup и update.json
   существующим `Publish-Release.ps1` из проверенных байтов архива.
5. Пока latest остаётся `common-v1.2.50` и тег 1.2.51 свободен, создать draft
   с тремя файлами. Скачать их обратно и сверить SHA, имена и target commit.
   Только затем опубликовать стабильный `common-v1.2.51` как latest. Старые
   архивы и выпуски не перезаписываются.
6. После освобождения блокировки публикации отдельный Ubuntu job запускает
   существующий `release-common.yml` с `--ref common-v1.2.51`. Тег закрепляет
   проверку на том же SHA независимо от последующих изменений main.
7. Дождаться именно нового workflow_dispatch-запуска на этом SHA. Проверить
   latest stable, публичный update.json, SHA/размер скачанного ZIP и содержимое
   setup по хешам файлов исходного Windows job. Не объявлять всех сотрудников
   обновлёнными до закрытия их браузеров.

Публикация останавливается при ошибке обязательного build, несовпадении
исходников/артефакта, занятом теге или неожиданной смене latest. Длительный
пятичасовой прогон предыдущего этапа относится к прежнему снимку исходников;
ему не приписывается проверка нового release commit. Подробности исправлений
и локальных замеров: `base-selection-validation.md`, `reliability-extended.md`.

## Первая Windows-проверка и диагностика

Первый publishing run `43559865227` остановился до создания выпуска:
419 из 420 Node-проверок прошли, а браузерный стенд в
`crm-base-catalog.test.cjs` не получил готовый DevTools endpoint за отведённое
число опросов. Исходная ошибка — `AssertionError: Chromium available`,
`actual: ''`. Проверки HTML в этом тесте ещё не запускались.
Отдельный Windows build `43559865206` на том же коммите прошёл; это не отменяет
отказ обязательной сборки. Общий канал сохранил версию 1.2.50.

Точный лог извлечён отдельной диагностикой `43560517072`. Одноразовый workflow
диагностики после этого удалён. Длинные annotations GitHub обрезает; новые
ошибки Node выводятся частями по 2000 символов, а полный лог сохраняется
артефактом. Дальнейшее исправление относится к ожиданию реальной готовности
Chromium в стенде; проверки продукта не отключаются и не повторяются до
случайного успеха.

Исправленный стенд использует общий дедлайн 20 секунд, буферизованный stderr,
резервный `DevToolsActivePort` и подтверждённый HTTP page target; ошибка или
выход процесса завершают ожидание сразу. 11 новых регрессий проверяют условия
запуска. Локальный полный прогон после исправления: 431/431, без пропусков;
независимый целевой прогон: 59/59 с настоящим Chromium. Все 25 сценариев HTML
и утверждения результатов сохранены побайтно. Для активации выпуска остаётся
обязательный успешный Windows build этого исправленного коммита.

Повторный run `43561373433` прошёл обязательный Windows build, семь PowerShell
suites и проверку точного архива. Проверенный ZIP: 525177 байт, SHA-256
`492da594fe9791a37bfe4a9a235a792da56f6fb3dfb262704f758b408cf14dac`.
На шаге публикации создался черновик `445039752` с тремя файлами; поиск этого
неопубликованного черновика через published-tag endpoint вернул HTTP 404.
Канал остался на 1.2.50. Это ошибка сценария публикации, а не основание
игнорировать проверку или перезаписывать выпуск.

Диагностика `43562773058` подтвердила ID, автора `github-actions[bot]`, исходный
commit `9320ec40a3fdf85d0484392bdbcdfad204625112` и неизменённые три актива.
Продолжение допускается только для этого известного неопубликованного
черновика, через ID, после повторной проверки метаданных и содержимого.
Существующие файлы не загружаются заново; опубликованные или чужие выпуски
не меняются. Перед активацией target обновляется на новый проверенный commit
при идентичности исходников расширения и установщика.

Run `43564423382` подтвердил Windows-проверки нового helper, но остановился
после отдельного target-only PATCH. Чтение по ID в диагностике `43565190712`
показало фактическое поведение GitHub: ID остаётся `445039752`, target стал
`78541ea463fe385de555fa6a3b68c3a842f57638`, а tag_name сменился на
`untagged-f2b4962be5a405f2bea1`. Три файла и их SHA не изменились, draft остаётся
неопубликованным. Проверка правильно остановила переход в этом состоянии.

Сценарий упрощается до одной мутации. До неё проверяются точная известная
пара alias/commit, ID, автор, заметки, содержимое всех файлов, исходники,
прежний stable и отсутствие общего тега. Затем один PATCH по release ID
одновременно задаёт `tag_name`, `target_commitish`, `draft=false` и
`make_latest=true`. Отдельного обновления target больше нет. Тест API-модели
учитывает наблюдённое переключение в untaged при неполном PATCH; случайные
alias, неизвестные промежуточные SHA и второй черновик с общим тегом
отклоняются. Опубликованный результат обязан иметь точные tag51/current SHA.
