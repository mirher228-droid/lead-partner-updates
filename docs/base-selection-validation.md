# Определение базы: изменения и замеры

Common 1.2.50, исходный main `0cdd091e417268cfe1bd5df7a00ab71d9e23ad93`.
Этап 14 ноября 2026 UTC. Интерфейс сохранён; работа остаётся локальной.
План: `base-selection-plan.md`. Память предыдущих этапов: `development-progress.md`.

## Изменения в поведении

Адаптер контекста и панель используют общий разбор КП/МНЧ/БТ и одно решение
о базе. До исправления корпус выявил 24 расхождения: неверная выбранная база
или требование ручного выбора при уже однозначных данных. Латинские и смешанные
метки, NFKC, невидимые символы и компактные `BT/MNC` обрабатываются одинаково.
Существующие приоритеты и категории услуг сохранены. Известный бренд без услуги
по-прежнему не доказывает базу; конфликтные направления требуют выбора.

Сравнение настоящих справочников больше не зависит от пробелов вокруг `/` и `|`.
Полное название вида работ с таким символом сохраняет самостоятельный смысл;
если нативные списки допускают разные трактовки, требуется ручной выбор.
Несколько подходящих услуг внутри одной базы сохраняют её оценку, оставляя
неоднозначный вид работ пустым. Более пяти совпавших видов работ не выдаются
за полностью проверенный каталог: ограниченный просмотр оставляет выбор ручным.

Новый `readWorkCatalog` читает одну живую форму и один список работ на базу
за сравнение. Виды услуг используют этот же локальный снимок. Расписание
не загружается: оно не участвует в выборе базы. Подготовка записи, её токены,
проверки и расписание обычной карточки сохраняют отдельный прежний путь.
Партнёр определяется по единственной подходящей активной записи нативного
справочника, включая `Партнёр № 007`. Раньше сравнение всегда шло с
`has_partner=0`, даже когда контекст уже содержал партнёра.

Повреждённый или неполный ответ CRM не считается доказанным пустым списком.
Ошибка одной сравниваемой базы оставляет ручной выбор. Отдельно проверены
ошибки JSON, пустые повреждённые группы, страницы входа, неправильные адреса
и посторонние HTML-списки. Целиком отключённое поле не считается доказанно
пустым справочником другой базы.

Одинаковые параллельные сравнения объединяются. Полные результаты сохраняются
на 10 секунд с ограничением размера кэша; кнопка повтора запускает свежую
проверку. Ключ учитывает сотрудника, аккаунт, диалог, клиента, услугу, город,
партнёра, источник, каталоги и поколение формы. Изменение этих данных во время
чтения не позволяет применить старое решение. Неудачные результаты не мешают
сразу повторить чтение после восстановления CRM.

Допустимость контекста также участвует в защите поздних ответов: сообщение
`ok/allowed/routeSafe=false` не должно позволять прежнему чтению снова включить
панель, даже если сотрудник и диалог остались теми же.

Панель не повторяет один поиск номера заявки внутри цепочки автоматического
выбора. Новые сведения о профиле, телефоне, источнике и личности запускают
нужную повторную проверку. Фокус окна не перезапускает незавершённое определение
с потерей ввода. Ручные поля переносятся безопасно, без чужих нативных ID.
Ручной выбор в рамках прежней идентичности объявления и подтверждённая карточка
сохраняют приоритет над автоматикой. Формат ключа выбора базы не меняется:
смена названия объявления обрабатывается прежним способом.

## Измерения на одинаковых искусственных данных

Сервис исполняется настоящий; ответы HTTP подменены, задержка каждого ответа —
200 мс. Это воспроизводимые измерения запросов и задержки стенда, а не замер
CRM или компьютеров сотрудников. Для «до» используется прежний путь
`dependencies`, поведение которого сохранено; для «после» — `readWorkCatalog`.

| Сравнение | Запросы до → после | Время до → после |
|---|---:|---:|
| 2 базы, только работы | 6 → 4 | 405 → 403 мс |
| 2 базы, 1 вид работ с услугами | 12 → 6 | 1016 → 602 мс |
| 2 базы, 2 вида работ с услугами | 18 → 8 | 1008 → 606 мс |
| 3 базы, 2 вида работ с услугами | 27 → 12 | 1006 → 632 мс |

Отдельный замер контроллера с ответами по 200 мс: два последовательных
одинаковых сравнения — 8 → 4 обращения и 855 → 448 мс. Два одновременных —
8 → 4 обращения; время остаётся около 402 мс, поскольку чтения уже шли
параллельно. Точный прежний исходник контроллера и его SHA сохранены на стенде.
Повтор с окончательными исходниками дал 4 обращения / 453 мс последовательно
и 4 / 402 мс одновременно; сервис — 18 → 8 запросов, 1008 → 605 мс.

В реальной панели Chromium при искусственном ответе через 90 мс поиск
неподтверждённого номера выполнялся трижды; теперь — один раз на цепочку.
Ожидание перед появлением выбора базы уменьшилось со 182 до 92 мс.
В интеграционном сценарии 50 одновременных уведомлений проходят всю цепочку
контекст → правила → контроллер → сервис с шестью GET суммарно.

Воспроизведение из корня репозитория:

```sh
node tools/benchmark_base_catalog.cjs legacy
node tools/benchmark_base_catalog.cjs optimized
node tools/benchmark_base_resolution.cjs
node --test
python -m unittest discover -s tests -p test_cloud_build.py
python tools/build_common.py
```

Проверка контроллера «до» поддерживает путь к сохранённому прежнему модулю
в первом аргументе `benchmark_base_resolution.cjs`. Времена меняются между
запусками; число запросов проверяется независимо от времени.
